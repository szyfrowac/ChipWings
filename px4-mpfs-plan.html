Progress and deviations, 9 November 2026

  • Steps 1–9 are done in Renode. Checks: sim/phase5/phase5_test.py (steps 5–6, and --flight for steps 7–8 and the isolation checks), sim/phase4/rpmsg_test.py, examples/run_examples.py. Details and gotchas are in sim/README.md, Phase 5.
  • Step 7: the NuttX layer did not scale task stacks for 64-bit pointers (PX4's POSIX layer does), so sih's 1560-byte stack overflowed into the heap. PX4 patch 0006 doubles them. Hover holds at 2.5 m with stress-ng on all three Linux harts.
  • Step 8: the board registers /dev/ttyRPMSG0 itself (rpmsg_tty.c), as planned. It sends nothing until Linux has sent a first message (OpenAMP learns Linux's endpoint address from it) and drops output when Linux has been silent for 3 s. mavlink -r is set to 100000 B/s; at 20000 the default streams throttled ATTITUDE to 10 Hz. Linux needs CONFIG_RPMSG_TTY=y.
  • New, not in the plan: link-loss failsafe defaults (NAV_DLL_ACT 3, COM_DL_LOSS_T 5): PX4 lands by itself when Linux's heartbeat stops, and refuses to arm without a data link. Tested with Linux frozen: lost after about 10 s, landed and disarmed after 25 s.
  • New: NuttX patch 0005 bounds the IHC notify retry budget (a failed notification cost about a second on the board; now about 1 ms), applied to both NuttX trees. build-px4.sh deletes stale NuttX objects when the board's defconfig changes.
  • Not done: the HSS boot rehearsal in Renode (addition B), --target board for rpmsg_test.py and run_examples.py (addition A), and the MSS watchdog (Phase 6). The perf latency check (99% within 25 µs with Linux running) is marginal at 98.7–99.2%.
  • Renode artifact: a panicked Linux (spinning harts) slows the simulation to about 0.03× real time, so timing checks that follow a panic use halted harts instead.

What changed in revision 3

  • The goal is now explicit: this software will eventually fly. Renode proves the logic; it does not prove the board. A new section, From Renode to the Icicle Kit, adds hardware rungs H0–H6 after the Renode steps.
  • Two additions before step 5: tests that run unchanged against Renode or a serial port, and a rehearsal of the HSS boot path in Renode.
  • New checks in steps 7 and 8: PX4 must keep holding hover while Linux is under full load, and while Linux panics.
  • Hardware status: Icicle Kit on hand with the 2025 reference design; power supply not yet delivered, so H0 onward waits for it. Renode steps 1–9 do not.

What changed from revision 1

  • The reference port is now STM32 (platforms/nuttx/src/px4/stm/), not RP2040 or ESP32.
  • The chip layer copies STM32's two-level layout: a microchip_common/ folder holding the code, and a thin mpfs/ folder that selects pieces and adds chip headers.
  • Every PX4 hardware hook is now mapped to its STM32 implementation and its MPFS equivalent, including the hooks we postpone, so later phases slot into the right place.
  • The board folder follows boards/px4/fmu-v6x (STM32H7), including selecting the timer in board_config.h.
  • Unchanged: the goal, the memory map, RPMsg to Linux, SIH for the closed loop, and the "written from scratch, nothing from TII" rule.
Rationale

Why STM32 is the right model

Copy the port PX4 itself is built around, not the smallest one. Every Pixhawk FMU from v2 to v6X runs on STM32. PX4's CI builds it on every commit, and the maintainers review changes against it. Its layer is the full set of services a flight controller needs. The RP2040 and ESP32 layers are community ports that implement the minimum to boot, so copying them would also copy their gaps.

What STM32 gives us that the small ports don't:

  • The intended folder structure. stm32_common/ holds the code, and each family folder (stm32f4, stm32f7, stm32h7) is a few CMake lines plus header overrides. Microchip has the same situation: PolarFire SoC and PIC64GX share the U54 core complex.
  • The full timer. STM32's hrt.c includes a latency histogram (perf latency) and selects its timer from board_config.h. RP2040's hrt.c is a cut-down copy of the same file.
  • The complete list of hooks: reset modes, UUID/MFGUID/PX4 GUID, hardware revision, SPI/I2C bus descriptions, PWM via io_timer, DShot, ADC, tone alarm, watchdog, crash dump. That tells us exactly what we are deferring, not just what we need today.

STM32 is the model for structure and completeness. Register-level code can't be copied, because the peripherals differ. Where STM32 relies on a hardware feature MPFS lacks, the table below says so.

The one real design difference: the timer

On STM32 the counter and the compare register belong to the same timer, so a deadline is an absolute counter value. MPFS has no MSS timer with a compare channel. Its free-running 64-bit counter is the CLINT, and the CLINT compare for hart 1 (mtimecmp) already drives the NuttX tick. NuttX on STM32 also keeps its tick (SysTick) separate from the PX4 timer, so splitting the two jobs follows the STM32 pattern.

The cost is that MSS Timer 1 is loaded with a relative delay, which adds a little skew. The latency histogram STM32 already keeps will show that skew. If it is too large, the fallback is to move the NuttX tick to MSS Timer 2 and give PX4 mtimecmp, which would mirror STM32 exactly but means patching NuttX's mpfs_timerisr.c.

Procedure

Steps

Each step changes one layer and ends in a check, so a failure points at the layer just added: build, then boot, then correct, then fast.

  1. Workspace and toolchain

    • sw/px4-chipwings/, sw/px4-patches/, sw/build-px4.sh.
    • A shim folder maps riscv64-unknown-elf-* to the xPack riscv-none-elf-* 15.2 tools, so PX4's toolchain file works unchanged.
    • Python requirements go into a venv at sw/px4-venv.

    Check: make chipwings_mpfs-hart1_default gets past CMake configure.

  2. Chip detection and the empty STM32-shaped skeleton

    • Patch px4_impl_os.cmake and board_common.h.
    • Create microchip/, microchip_common/ and mpfs/ with the CMake wiring copied line for line from stm/ and stm32h7/, and empty sources.

    Check: everything compiles and the link fails only on undefined hrt_* and board_* symbols. That list is the to-do list for step 4.

  3. Board skeleton, following fmu-v6x

    • Create the files in the layout above.
    • Build nsh/defconfig from our Phase 4 config, then add what PX4 needs from NuttX: ROMFS, boardctl, work queues, instrumentation for top, tmpfs. Find that list by diffing against boards/px4/fmu-v6x/nuttx-config/nsh/defconfig.
    • board_config.h carries the same kinds of defines as fmu-v6x's: HRT timer, LED, PWM count.

    Check: the only link errors left are the chip-layer symbols.

  4. Chip layer, in STM32's order

    • Write the headers first. Use STM32's micro_hal.h as the template and replace each stm32_* mapping with its mpfs_* call; anything with no counterpart gets a comment saying why.
    • Then version, board_reset and board_critmon, keeping STM32's function bodies' structure.
    • hrt.c last. Take STM32's file and keep the callout queue, hrt_call_*, hrt_ioctl hooks and latency code. Replace hrt_tim_init, hrt_tim_isr, hrt_absolute_time and the compare write in hrt_call_reschedule. Drop the PPM block.
    • Before moving on, diff each file against its STM32 original and confirm every difference is deliberate. This is the review method for the whole port.

    Check: px4.elf links; its memory use fits the regions below.

  5. First boot, PX4 alone on hart 1

    sim/phase5/px4.resc loads px4.elf on u54_1 only; Linux stays off.

    Check: ver all, uorb top, work_queue status, top and param show work. tests hrt passes. perf latency shows most callouts in the 1–5 µs buckets. hrt_absolute_time advances 1,000,000 per simulated second.

  6. RPMsg back on

    init.cpp starts rptun the way cwinit did. Linux boots on harts 2–4 as in Phase 4.

    Check: sim/phase4/rpmsg_test.py 500 passes 500/500 against PX4's NuttX; hartcheck and rpmsg_ping pass.

  7. Closed loop with SIH

    Enable simulator_sih, sensors, ekf2, the multicopter controllers, commander, navigator, land_detector and mavlink. Select airframe 1100_rc_quad_x_sih, which sets SYS_HITL 2.

    Check: commander arm, commander takeoff; listener vehicle_local_position shows z near −2.5 m and holding; ekf2 status shows no faults. Record CPU load and the Renode-to-real-time ratio.

    Isolation checks (new): while hovering, (a) run stress-ng on all three Linux harts: the hover holds and perf latency does not shift; (b) panic Linux with echo c > /proc/sysrq-trigger: PX4 keeps hovering and lands on its own failsafe when the MAVLink link drops. A flight controller must not depend on Linux staying healthy.

  8. MAVLink to Linux over RPMsg

    rpmsg_tty.c registers /dev/ttyRPMSG0 on endpoint rpmsg-tty with raw bytes, which Linux's rpmsg_tty driver accepts. NuttX's uart_rpmsg adds a header that Linux's driver rejects. PX4 runs mavlink start -d /dev/ttyRPMSG0 -m onboard. A new Linux example, mavlink_link, prints HEARTBEAT and ATTITUDE and sends arm and takeoff.

    Check: HEARTBEAT arrives at 1 Hz and ATTITUDE has no gaps in sequence numbers for 60 s; the vehicle takes off on Linux's command.

  9. Tests and docs

    sim/phase5/run.sh, phase5_test.py covering steps 5–8, sim/README.md, and the Linux guide updated with results.

Method

How to port PX4 to any new chip

  1. Read the project's own guidance first: docs/en/hardware/porting_guide*.md, AGENTS.md, and .github/instructions/* for boards/** and platforms/**.
  2. Prove the OS alone first. We did that in Phases 1–4. Never debug the RTOS and the flight stack together.
  3. Take the native port as the model. For PX4 that is STM32: it defines what the layer is supposed to contain and how it is organized. Small community ports show only what is enough to boot. Read vendor forks only to confirm an approach.
  4. Map every hook before writing one. List each piece of the native layer with your chip's equivalent, now or later. This catches missing hardware (a compare channel, a unique ID) at design time.
  5. Let the linker write the to-do list. Wire detection and an empty layer, build, then implement exactly the undefined symbols.
  6. Timer first, tested hardest, with the native port's latency instrumentation kept.
  7. Diff against the reference. Each ported file should differ from its native original only where the hardware forces it.
  8. Keep the port outside the upstream tree: own folder, small patches, one apply script.
  9. Bring up in layers with a check at each: build, shell, built-in tests, simulation on the chip (SIH), then real I/O.
